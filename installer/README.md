# Распространение: тонкий загрузчик и компоненты

## Зачем так

Дистрибутив занимает 4.5 ГБ, из них 74% — `torch` с библиотеками CUDA, которые
меняются раз в полгода. Собственный код продукта весит около двух мегабайт. Раздача
одним архивом означала бы загрузку полутора гигабайт ради правки в пару мегабайт,
поэтому дистрибутив разделён по частоте изменений.

| Компонент | Архив | Развёрнуто | Обновляется |
|---|---|---|---|
| `runtime` — torch, CUDA, cuDNN | 1199 МБ | 3270 МБ | раз в полгода |
| `ffmpeg` — декодер медиафайлов | 109 МБ | 434 МБ | практически никогда |
| `app` — приложение, Qt, научные библиотеки, ядро conform | 254 МБ | 814 МБ | при каждом выпуске |

Сам загрузчик — 13 МБ: окно (`tkinter` входит в состав Python), распаковщик 7-Zip и
контрольный материал. Ни `torch`, ни Qt, ни ядра conform в нём нет.

## Свойство, ради которого всё построено

`manifest.json` описывает компоненты **именем файла и контрольной суммой**, а не адресом
загрузки. Из этого следует:

* файлы можно разместить где угодно — облачное хранилище, съёмный носитель, сетевой
  каталог; загрузчику безразлично, каким путём они получены;
* полученные заранее архивы распознаются автоматически: поиск идёт в каталоге установки
  и в подкаталоге `packages`, а если файл переименован — по размеру и контрольной сумме;
* `url` в манифесте необязателен и нужен лишь для загрузки по сети, когда файлов нет.

Порядок работы загрузчика:

```
манифест → поиск архивов (локально либо загрузка) → сверка SHA-256 → распаковка →
проверка установки обработкой → запуск приложения
```

**Проверка установки** — не наличие файлов: контрольный материал (40 секунд, звук
намеренно сдвинут на 350 мс) проходит полный конвейер через API приложения, и контрольная
сумма результата сверяется с эталонной. Так выявляются и неполная распаковка, и
несовместимый набор библиотек. Проверка занимает 3–6 секунд.

## Раскладка на машине пользователя

```
conform-setup.exe          загрузчик
packages\                  файлы установки (можно принести заранее)
    manifest.json
    conform-runtime-<версия>.7z
    conform-ffmpeg-<версия>.7z
    conform-app-<версия>.7z
app\                       развёрнутый дистрибутив (создаётся загрузчиком)
    conform-desktop.exe
    installed.json         какие компоненты установлены (контрольные суммы)
```

Права администратора не требуются, установка идёт в каталог рядом с загрузчиком.

## Выпуск новой версии

```bash
# 1. собрать дистрибутив и снять с него лишнее
cd build
python -m PyInstaller conform-desktop.spec --noconfirm --workpath ..\_work --distpath ..\dist
python prune_dist.py --dist ..\dist\conform-desktop --apply

# 2. нарезать на компоненты и составить манифест
cd ..
python installer\split_dist.py --dist dist\conform-desktop --out installer\packages ^
    --base-url https://github.com/<владелец>/conform-desktop/releases/download/<тег>

# 3. пересобрать загрузчик (нужен только при изменении самого загрузчика)
cd installer
python -m PyInstaller launcher.spec --noconfirm --workpath ..\_work_setup --distpath ..\dist_setup

# 4. проверить установку с нуля на чистом каталоге
#    (файлы кладутся в packages, сети не требуется)
conform-setup.exe --check      # 0 — установка исправна, 1 — нет
```

Ограничение GitHub — 2 ГБ на файл в разделе Releases; самый крупный компонент (1199 МБ)
в него укладывается. Сборка автоматизирована (см. «Автоматическая сборка и выпуск» ниже),
но выпуск можно готовить и локально — тогда публикуются уже принятые артефакты.

## Обновление эталона проверки

Эталон привязан к конкретной сборке: изменения в алгоритме меняют результат обработки, и
контрольная сумма перестанет совпадать. Снимается так же, как принимается сборка, —
прогоном контрольного материала через API и записью суммы в `installer/selfcheck.json`
(`ref_check.mkv`, `dub_check.mkv` лежат в `installer/selfcheck/`).

Обязательное условие: перед записью эталон прогоняется **не менее двух раз** и суммы
обязаны совпасть. Невоспроизводимый эталон превращает проверку в источник ложных
сообщений о неисправности.

## Что ещё стоит сделать

Компонент `app` (254 МБ) содержит и наш код, и стабильные библиотеки (Qt, научный стек).
Их разделение на `libs` и `core` уменьшит обновление до единиц мегабайт: при правке
алгоритма меняется только `core`.

## Автоматическая сборка и выпуск

Два потока в `.github/workflows/`:

| Поток | Когда | Что делает |
|---|---|---|
| `checks.yml` | каждое изменение в `main` и запрос на слияние | компиляция модулей; сверка ключей перевода; проверка строк интерфейса на жаргон по словарю; сборка тонкого загрузчика и проверка, что без файлов он честно завершается отказом |
| `release.yml` | тег `v*` либо вручную | полная сборка дистрибутива, снятие лишнего, нарезка на компоненты с манифестом, сборка загрузчика со встроенным адресом выпуска, публикация. Ручной запуск ничего не публикует — только собирает |

Проверки уже окупились: сверка словаря нашла жаргон на вкладке «Задача»
(«озвучки», «дубль», «= реф»), а сборка на англоязычной Windows — падение вывода в
`cp1252` при печати русского сообщения. Оба дефекта существовали в продукте и на нашей
машине не проявлялись.

⚠ Тонкий загрузчик собирается в двух видах: оконный для людей и консольный
(`LAUNCHER_CONSOLE=1`) для проверок. У оконного нет стандартного вывода, и режим
`--check` из консоли не отвечает вовсе — шаг проверки однажды провисел 25 минут.

**Публикация выпуска вручную** (когда компоненты уже собраны и приняты локально):

```bash
gh release create v<версия> --title "conform-desktop <версия>" --notes-file notes.md --draft
gh release upload v<версия> dist_setup/conform-setup.exe installer/packages/manifest.json     installer/packages/*.7z
gh release edit v<версия> --draft=false
```

Перед загрузкой в манифесте проставляются адреса компонентов на тег выпуска, а загрузчик
пересобирается с `manifest_url.txt`, указывающим на `manifest.json` этого же выпуска, —
иначе у пользователя с одним лишь загрузчиком не будет состава.
